# C1 — Ledger Core: sequenced build prompts

> **Background (history).** Written during the design and build phase and kept as a
> record. You don't need it to run or change today's product: start at
> [docs/README.md](../README.md).

**Target:** Go + PostgreSQL. **Consumer:** an AI coding agent (Claude Code or equivalent).

**How to use this file.** Paste §0 once at the start of the session — it is standing context the agent must hold for every chunk. Then paste chunks C1.0 → C1.10 one at a time, in order. Do not move to the next chunk until the current chunk's acceptance criteria pass. Each chunk is deliberately small enough to review in one sitting.

**Before you start:** read §A (chart of accounts) and §B (the worked conversion entry). §B is the crux design decision of the whole ledger — if it is wrong, everything built on top is wrong. Review it yourself before handing any of this to an agent.

## §0 — Standing context (paste once)

```
You are building C1, the ledger core of a USDT cross-network settlement system
(BEP20 → TRC20 payouts). This is the first component built; five other services
will be clients of it over HTTP.

STACK
- Go 1.22+, PostgreSQL 16
- pgx/v5 for Postgres. No ORM. Hand-written SQL.
- goose for migrations
- Standard library net/http with chi for routing
- log/slog for structured logging
- testify for assertions, testcontainers-go for integration tests against real Postgres

WHAT C1 IS
The single source of truth for money and order state. Double-entry, append-only,
multi-asset. It records what happened, enforces that the books balance, drives the
order state machine, reconciles itself against externally reported chain balances,
and halts outbound money movement when it cannot.

WHAT C1 IS NOT — do not build any of this, do not import libraries for it
- No blockchain RPC of any kind. C1 never talks to BSC or TRON.
- No private keys, no signing, no wallets.
- No pricing, fee tiers, or quote calculation. C1 records amounts it is given.
- No vendor integrations (screening, energy providers, exchanges).
- No customer-facing auth. That is C6.
- No sweeping, batching, or transaction construction.
If a chunk seems to require any of the above, you have misread it. Stop and say so.

NON-NEGOTIABLE INVARIANTS
1. No floating point anywhere in the money path. All amounts are signed integers in
   minor units (6 decimal places for USDT_BEP20, USDT_TRC20, TRX; 18 for BNB —
   store BNB in gwei-equivalent int64 and document the truncation, it is only ever
   a gas cost). Postgres column type is NUMERIC(38,0) holding minor units, never
   NUMERIC(x,y) with a scale and never float/double.
2. The journal is append-only. No UPDATE, no DELETE, ever, enforced at the database
   role level, not merely by convention. Corrections are reversing entries.
3. Every journal entry balances to exactly zero per asset. An entry may touch more
   than one asset; each asset within it sums to zero independently.
4. Every write is idempotent on a caller-supplied key. Same key + same payload
   returns the original result. Same key + different payload is a hard error, never
   a silent accept and never a second write.
5. USDT_BEP20 and USDT_TRC20 are DIFFERENT ASSETS. They are never netted, never
   summed together, and never implicitly converted. The whole product is the
   controlled exchange between them.
6. All timestamps are UTC and generated by the database, not the application.
   `occurred_at` (when the real-world event happened, supplied by the caller) is
   distinct from `recorded_at` (when we learned of it, set by the DB).
7. Money can only leave the system through a state transition that is blocked while
   the system is halted.

STYLE
- Small packages with explicit boundaries: internal/money, internal/accounts,
  internal/journal, internal/orders, internal/recon, internal/httpapi.
- Errors are typed sentinel values or structs, wrapped with %w. Every error that
  can reach the HTTP layer maps to exactly one stable error code.
- Every exported function that writes has a context.Context first parameter and
  participates in a caller-supplied transaction where correctness requires it.
- Tests are the deliverable, not an afterthought. A chunk is not done when the code
  compiles; it is done when its acceptance tests pass against real Postgres.
- Do not add features, endpoints, or abstractions that a chunk did not ask for.
```

## C1.0 — Scaffold and the money type

```
Build the repository skeleton and the money primitive. Nothing else.

1. Go module `ledger`. Layout:
   cmd/ledgerd/main.go
   internal/money/
   internal/db/
   migrations/
   docker-compose.yml (Postgres 16 only)
   Makefile (targets: build, test, test-integration, migrate-up, migrate-down, lint)

2. internal/money:
   - type Asset string, with the closed set: USDT_BEP20, USDT_TRC20, TRX, BNB.
     Unknown asset strings must fail to parse, not default.
   - Each asset has a fixed Decimals value (USDT_BEP20 6, USDT_TRC20 6, TRX 6, BNB 9
     — document that BNB is truncated to gwei and is only ever a gas expense).
   - type Amount struct { Asset Asset; Units int64 }  // Units are minor units, signed
   - Add, Sub, Neg. Every operation returns (Amount, error).
     - Adding two different assets is an error. Not a panic, not a coercion.
     - Overflow is an error. Use explicit checked arithmetic; do not rely on wrap.
   - Parse/Format helpers: ParseDecimal("2990.700000", USDT_TRC20) -> Units 2990700000,
     and the inverse. Reject more decimal places than the asset allows — do NOT round.
   - Zero-value Amount (empty Asset) must be rejected by every operation.

3. internal/db: pgx pool setup, config from env, a Tx helper that runs a function in a
   transaction and rolls back on error or panic.

4. Migration 0001: create the database role split described below (see acceptance),
   nothing else yet.

5. cmd/ledgerd: starts, connects, serves GET /healthz returning 200 with build info,
   shuts down cleanly on SIGTERM.

ACCEPTANCE
- `make test` green.
- Property test (use testing/quick or a loop with a seeded PRNG, 100k iterations):
  for random int64 pairs, Add/Sub either return a correct result or an overflow
  error — never a wrong number, never a panic.
- Table test: ParseDecimal rejects "1.0000001" for a 6-decimal asset, rejects "1e5",
  rejects "", rejects "-0.5" only if negative is disallowed at the parse site
  (it is not — negatives are legal, credits exist).
- Round-trip test: Format(Parse(x)) == x for 1000 generated decimal strings.
- Migration 0001 creates two Postgres roles: `ledger_writer` (INSERT + SELECT) and
  `ledger_reader` (SELECT only). Prove with a test that ledger_writer cannot UPDATE
  or DELETE on a scratch table — the grant model is what enforces append-only, so it
  must be verified now, before there is anything to protect.
- No file in internal/money imports anything outside the standard library.

DO NOT
- Do not create any accounting tables yet.
- Do not add a generic "Decimal" or big.Rat type. int64 minor units only.
```

## C1.1 — Chart of accounts

```
Build the account model. Accounts only — no entries yet.

TABLE accounts
  id            bigserial primary key
  code          text not null unique      -- hierarchical, see below
  type          account_type not null     -- enum: ASSET, LIABILITY, REVENUE, EXPENSE, EQUITY, POSITION
  asset         asset_code not null       -- enum matching internal/money
  normal_side   smallint not null         -- +1 debit-normal, -1 credit-normal, 0 for POSITION
  is_active     boolean not null default true
  opened_at     timestamptz not null default now()
  metadata      jsonb not null default '{}'

RULES
- An account has exactly ONE asset for its whole life. USDT_BEP20 and USDT_TRC20
  balances live in different accounts even when they describe the same wallet.
- normal_side is derived from type and must be consistent: ASSET/EXPENSE = +1,
  LIABILITY/REVENUE/EQUITY = -1, POSITION = 0. Enforce with a CHECK constraint.
- Account codes are colon-delimited and parseable:
    asset:bsc:deposit:<order_id>          per-order deposit address
    asset:tron:slot:<slot_id>             one of the six payout slots
    asset:cex:<venue>                     rebalancing venue balance
    asset:tron:energy_wallet              TRX held for energy/bandwidth
    liability:customer:<customer_id>      what we owe a customer
    position:corridor                     the BEP20/TRC20 inventory position (see §B)
    revenue:fee                           bp fee
    revenue:network_fee                   the per-payout network fee line
    expense:energy                        TRX spent on energy rental
    expense:bandwidth                     TRX spent on bandwidth
    expense:gas                           BNB spent on BSC
    expense:rebalance                     cost of moving inventory between chains
    expense:loss:reorg                    realised loss when a reorg lands post-payout
    expense:loss:freeze                   realised loss when a slot is frozen
    equity:opening                        opening balances only
- Account creation is idempotent on code.
- Accounts are never deleted. Deactivation sets is_active=false; a deactivated
  account may still be read but may not be debited or credited.

BUILD
- internal/accounts: Create(ctx, code, type, asset), GetByCode, List(filter).
- A seed function that creates every account above whose code has no variable part,
  runnable repeatedly without error.
- A code parser: given "asset:tron:slot:3", return the segments in a typed struct so
  other components can dispatch on them without string surgery.

ACCEPTANCE
- Creating an account with mismatched type/normal_side is rejected by the DB, not
  just by Go. Test it by inserting raw SQL that bypasses the Go layer.
- Creating the same code twice returns the same account id, no error.
- Seeding twice is a no-op.
- An attempt to create `asset:tron:slot:1` with asset USDT_BEP20 succeeds (the model
  does not know about chain/asset pairings — that is C5's business) but a test
  documents this explicitly so the choice is deliberate.
```

## C1.2 — The journal

```
Build the append-only, multi-asset, balanced journal. This is the heart of C1.

TABLE journal_entries
  id               bigserial primary key
  idempotency_key  text not null unique
  payload_hash     bytea not null            -- sha256 of the canonical request
  entry_type       text not null             -- e.g. deposit_final, conversion, payout_settled
  order_id         bigint null               -- FK added in C1.5
  actor            text not null             -- which service wrote this
  occurred_at      timestamptz not null      -- caller-supplied, real-world time
  recorded_at      timestamptz not null default now()
  reversal_of      bigint null references journal_entries(id)
  metadata         jsonb not null default '{}'

TABLE journal_lines
  entry_id      bigint not null references journal_entries(id)
  seq           smallint not null
  account_id    bigint not null references accounts(id)
  asset         asset_code not null
  amount_units  numeric(38,0) not null    -- POSITIVE = DEBIT, NEGATIVE = CREDIT
  primary key (entry_id, seq)

SIGN CONVENTION — state it in a doc comment and never deviate:
  positive amount_units = debit, negative = credit.
  For every entry, and for every asset within that entry, SUM(amount_units) = 0.

ENFORCEMENT — all three layers, not one:
1. Go: validate before the INSERT. Reject empty entries, single-line entries,
   zero-amount lines, lines whose asset differs from their account's asset, and any
   per-asset sum != 0.
2. Postgres: a CONSTRAINT TRIGGER on journal_lines, DEFERRABLE INITIALLY DEFERRED,
   that at COMMIT time recomputes the per-asset sum for every touched entry and
   raises if any is non-zero. This is what makes the invariant true even if someone
   writes SQL by hand.
3. Postgres: rules or triggers that raise on UPDATE and DELETE for both tables, plus
   the role grants from C1.0.

BUILD internal/journal
  type Line struct { AccountCode string; Amount money.Amount }
  type EntryRequest struct {
    IdempotencyKey string
    EntryType      string
    Actor          string
    OccurredAt     time.Time
    OrderID        *int64
    Lines          []Line
    Metadata       map[string]any
  }
  Post(ctx, tx, EntryRequest) (Entry, error)

  - Canonical payload hash: serialise {entry_type, order_id, sorted lines by
    (account_code, asset, amount), occurred_at truncated to microseconds} as
    deterministic JSON, sha256 it. Sorting matters — line order must not change the
    hash.
  - Post must be usable inside a caller's transaction so a balance update (C1.4) and
    a state transition (C1.5) commit atomically with the entry.

ACCEPTANCE
- Unbalanced entry rejected in Go AND, when Go is bypassed with raw SQL, at COMMIT
  by the trigger. Write both tests.
- A two-asset entry where each asset balances independently is ACCEPTED. This is the
  conversion shape from §B and must work.
- A two-asset entry where the combined sum is zero but one asset is +5 and the other
  is -5 is REJECTED.
- UPDATE and DELETE on journal_entries and journal_lines both raise, as ledger_writer
  and as the table owner.
- Line whose asset != its account's asset is rejected.
- Entry with zero lines, one line, or any line with amount 0 is rejected.
```

## C1.3 — Idempotency

```
Make Post idempotent under concurrency. No new tables.

SEMANTICS — implement exactly this, no variations:
- Key not seen: insert, return the new entry, mark result as Created.
- Key seen, payload_hash identical: return the ORIGINAL entry, mark result as
  Replayed. No second row. No error.
- Key seen, payload_hash different: return ErrIdempotencyConflict with both hashes
  in the error. Write nothing. This is a bug in the caller and must be loud.

IMPLEMENTATION
- Rely on the unique index, not on a read-then-write check — a check is a race.
  INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING id; if no row came
  back, SELECT the existing row and compare payload_hash.
- Key format convention (document it, enforce a max length of 255):
  "<producer>:<domain>:<natural-id>", e.g.
    watcher:deposit_final:0xabc...:12       (tx hash + log index)
    dispatcher:payout_settled:<tron_txid>
    ledger:reverse:<original_key>
  The natural id must come from the external world, not from a UUID generated at
  call time — a retried call must generate the SAME key.

ACCEPTANCE
- 1,000 goroutines Post the same key with the same payload concurrently against real
  Postgres: exactly one row exists, all 1,000 calls return the same entry id, exactly
  one reports Created.
- Same key, one byte different in the payload: conflict error, still one row.
- Line reordering does not change the hash: two calls with lines in different order
  and the same key both succeed as Created + Replayed.
- occurred_at differing by less than a microsecond does not change the hash;
  differing by more does.
```

## C1.4 — Balances

```
Two balance paths that must always agree.

TABLE account_balances
  account_id     bigint primary key references accounts(id)
  asset          asset_code not null
  balance_units  numeric(38,0) not null default 0
  last_entry_id  bigint not null              -- watermark
  updated_at     timestamptz not null default now()

This table is the ONLY mutable table in the money path, and it is a cache. It is
updated in the SAME transaction as the journal insert, never afterwards, never by a
background job.

BUILD internal/journal (extend)
- Post also applies each line to account_balances via UPDATE ... SET balance_units =
  balance_units + $1, last_entry_id = $entry. Row-level locks make this serialisable;
  take the account rows in ascending account_id order inside every entry to make
  deadlock impossible.
- Balance(ctx, accountCode) (money.Amount, error) — reads the cache.
- BalanceComputed(ctx, accountCode) — SUM over journal_lines. Slow path.
- BalanceAsOf(ctx, accountCode, maxEntryID) — SUM over journal_lines where
  entry_id <= maxEntryID. This is what reconciliation needs, because a chain
  snapshot is taken at a moment and the ledger keeps moving.
- VerifyBalances(ctx) — for every account, cache vs computed; returns a list of
  discrepancies. Must be cheap enough to run every minute.
- TrialBalance(ctx) — per asset, SUM over ALL accounts. Must be exactly 0 for every
  asset. This is double-entry closure and it is the single strongest health signal
  in the system.

ACCEPTANCE
- After 10,000 randomly generated valid entries, VerifyBalances finds nothing and
  TrialBalance is 0 for every asset.
- Deadlock test: 200 goroutines posting entries that touch overlapping account sets
  in random order — zero deadlocks over the run, because of the ordering rule.
- BalanceAsOf(account, N) equals the cache balance after exactly N entries, replayed.
- Deliberately corrupt account_balances with raw SQL: VerifyBalances reports it and
  names the account.

DO NOT
- Do not add a background reconciliation of the cache. If the cache can drift from
  the journal without the transaction failing, the design is wrong — fix the
  transaction, do not add a repair job.
```

## C1.5 — Order state machine

```
TABLE orders
  id                bigserial primary key
  external_id       text not null unique     -- the id C6 gave the customer
  customer_id       text not null
  tier              order_tier not null      -- enum: DIRECT, STANDARD, SWEEP
  state             order_state not null
  amount_in         numeric(38,0) not null   -- USDT_BEP20 minor units
  amount_out        numeric(38,0) not null   -- USDT_TRC20 minor units, quoted
  fee_units         numeric(38,0) not null
  network_fee_units numeric(38,0) not null
  recipient_address text not null
  quoted_at         timestamptz not null
  quote_expires_at  timestamptz not null
  version           integer not null default 0
  created_at        timestamptz not null default now()
  updated_at        timestamptz not null default now()

TABLE order_transitions   -- append-only, same enforcement as the journal
  id           bigserial primary key
  order_id     bigint not null references orders(id)
  from_state   order_state not null
  to_state     order_state not null
  entry_id     bigint null references journal_entries(id)
  actor        text not null
  reason       text not null
  occurred_at  timestamptz not null
  recorded_at  timestamptz not null default now()

STATES: quoted, funded, screened, dispatching, settled, held, refunded, expired
TERMINAL: settled, refunded, expired

TRANSITION TABLE — encode this as a static Go map, the only source of truth.
Any pair not listed is illegal.

  from         to           requires entry   halt-blocked   notes
  quoted    -> funded       YES              no             deposit reached 15 conf
  quoted    -> expired      no               no             quote_expires_at passed, nothing received
  funded    -> screened     no               no             screening verdict pass
  funded    -> held         no               no             screening verdict hold
  funded    -> refunded     YES              YES            customer cancel pre-conversion
  funded    -> quoted       YES (reversal)   no             deposit reorged out
  held      -> screened     no               no             manual release, actor required
  held      -> refunded     YES              YES            manual reject
  screened  -> dispatching  YES              YES            posts the conversion entry (§B)
  dispatching -> settled    YES              YES            payout SR-final
  dispatching -> held       YES (reversal)   no             non-retryable failure; reverses conversion
  settled   -> (nothing)    -                -              terminal, no exceptions

RULES
- Retries of a payout are attempts INSIDE `dispatching`, not state changes. Do not
  add a state for them. Add a `dispatch_attempts` table if C5 needs one later; C1
  does not model it now.
- A transition marked "requires entry" must be called with a journal EntryRequest and
  both commit in one transaction, or neither does.
- A transition marked "halt-blocked" returns ErrSystemHalted while the halt flag is
  set (C1.7). Note that quoted->funded is NOT halt-blocked: we must keep recording
  inbound reality while halted. Only money leaving is blocked.
- Optimistic concurrency: Transition takes expectedVersion; a CAS miss is
  ErrVersionConflict, never a retry-in-place.
- Every transition writes an order_transitions row including the illegal-attempt
  case? No — illegal attempts are rejected before any write and logged, not stored.

BUILD internal/orders
  Create(ctx, OrderParams) (Order, error)     -- always starts in `quoted`
  Transition(ctx, orderID, toState, expectedVersion, TransitionParams) (Order, error)
  Get / GetByExternalID / ListByState

ACCEPTANCE
- Exhaustive test over the full 8x8 state cross product: exactly the 11 listed pairs
  succeed, the other 53 return ErrIllegalTransition, and no row is written for the
  failures.
- A transition that requires an entry, called without one, fails and writes nothing.
- A transition whose journal entry is unbalanced fails and leaves the order state
  unchanged — prove by asserting state and version after the failed call.
- Concurrent Transition with the same expectedVersion from 50 goroutines: exactly one
  succeeds, 49 get ErrVersionConflict.
- A settled order rejects every further transition.
```

## C1.6 — Reversals and reorg handling

```
No deletes, no edits. Corrections are new entries that negate old ones.

BUILD internal/journal (extend)
  Reverse(ctx, tx, originalEntryID, actor, reason, occurredAt) (Entry, error)
  - Builds an entry with every line's amount negated, same accounts, same assets.
  - reversal_of = originalEntryID.
  - idempotency_key = "ledger:reverse:" + original.idempotency_key.
  - UNIQUE index on reversal_of: an entry can be reversed AT MOST ONCE.
  - A reversal cannot itself be reversed. Reject it.

REORG SCENARIOS — implement both, they are not the same problem:

A. Reorg BEFORE dispatch (recoverable, expected, must be routine)
   Order is in `funded`. C2 reports deposit.reorged.
   -> Reverse the deposit_final entry.
   -> Transition funded -> quoted.
   -> If the quote has since expired, the very next call moves it quoted -> expired.
   Net effect on the books: zero. No loss account touched.

B. Reorg AFTER dispatch (the loss case, must be impossible to handle silently)
   Order is in `dispatching` or `settled`. The BEP20 deposit that funded a payout we
   have already made no longer exists.
   -> Reverse the deposit_final entry (the inbound is gone).
   -> Do NOT reverse the payout entry. The TRC20 left. It is gone.
   -> Post a loss entry to expense:loss:reorg for the full amount_out.
   -> Set the system halt (C1.7) with reason POST_SETTLEMENT_REORG.
   -> The order stays `settled`. It really did settle. We just were not paid.
   This path must be impossible to trigger without producing a halt. Write the test
   that asserts the halt fires.

  Provide: HandleDepositReorg(ctx, orderID, originalEntryKey, actor) which branches
  on the order's current state and refuses to guess — an unexpected state is an
  error, not a default branch.

ACCEPTANCE
- Reverse twice on the same entry: second call errors, one reversal row exists.
- Trial balance is exactly 0 per asset after every reorg scenario, A and B.
- Scenario A: order returns to `quoted`, all balances back to pre-deposit values.
- Scenario B: expense:loss:reorg holds exactly amount_out, halt is set, halt reason
  is POST_SETTLEMENT_REORG, and the order is still `settled`.
- HandleDepositReorg called on an order in `expired` returns an error naming the
  state, rather than doing nothing or doing something plausible.
```

## C1.7 — Reconciler and halt

```
The component that makes the ledger trustworthy rather than merely tidy.

TABLE system_state           -- single row, id = 1, this one IS mutable
  id             smallint primary key default 1 check (id = 1)
  halted         boolean not null default false
  halt_reason    text null
  halt_detail    jsonb null
  halted_at      timestamptz null
  halted_by      text null
  cleared_at     timestamptz null
  cleared_by     text null

TABLE halt_log               -- append-only history of every set and clear

TABLE recon_snapshots        -- append-only
  id             bigserial primary key
  account_id     bigint not null references accounts(id)
  asset          asset_code not null
  observed_units numeric(38,0) not null   -- what the chain says
  chain_ref      text not null            -- block height / hash, opaque to C1
  ledger_units   numeric(38,0) not null   -- BalanceAsOf at watermark
  watermark      bigint not null          -- max journal entry id considered
  drift_units    numeric(38,0) not null
  observed_at    timestamptz not null
  recorded_at    timestamptz not null default now()

INPUT
  POST /v1/reconciliation/snapshots — C2 and C5 report what the chain actually holds
  for an account they own, at a stated chain reference, with the ledger watermark
  they believe corresponds to it. C1 does not fetch anything. C1 does not know what a
  block is.

RECONCILIATION
- drift = observed_units - BalanceAsOf(account, watermark)
- Tolerance is per asset and configurable. DEFAULT FOR ALL USDT ASSETS IS ZERO.
  USDT is 6dp and exact; any non-zero drift is real. A non-zero tolerance may be
  configured for TRX only, to absorb energy/bandwidth rounding, and it must be
  logged loudly at startup when set.
- Non-zero drift beyond tolerance -> set halt, reason BALANCE_DRIFT, detail carrying
  account code, both figures, watermark, chain_ref.

SELF-CHECKS on a ticker (default 60s), independent of external snapshots:
- TrialBalance() == 0 for every asset. Failure -> halt, reason TRIAL_BALANCE_BROKEN.
- VerifyBalances() empty. Failure -> halt, reason CACHE_DIVERGENCE.
- position:corridor per-asset magnitude within a configured ceiling. Exceeding it is
  not necessarily an error — it means the treasury rebalance is behind — so this
  raises an alert, NOT a halt. Get this distinction right: halting on a slow
  rebalance would stop the business for a non-error.

HALT SEMANTICS
- Blocks every transition marked halt-blocked in C1.5. Nothing else.
- Does NOT block: deposit recording, reversals, reads, snapshot ingestion, or
  loss entries. You must be able to keep observing and correcting while halted.
- Clearing is manual only, requires an operator identity and a free-text note, and
  is recorded in halt_log. There is no auto-clear. Do not add one.
- The halt flag is cached in memory with a max staleness of 1 second and is
  re-read inside the transaction of any halt-blocked transition — a cached read is
  for fast rejection, the transactional read is what is authoritative.

ACCEPTANCE
- Inject 1 minor unit of drift on a USDT account: halt fires on the next cycle, with
  the account named in halt_detail.
- While halted: screened->dispatching returns ErrSystemHalted; quoted->funded
  succeeds; reads succeed; a reversal succeeds.
- Clearing without an operator id is rejected.
- Corrupt account_balances by hand -> CACHE_DIVERGENCE halt within one cycle.
- Post an unbalanced entry via raw SQL bypassing every Go check -> the C1.2 trigger
  should already have refused it; if it somehow lands, TRIAL_BALANCE_BROKEN halts
  within one cycle. Test the second line of defence, not just the first.
- position:corridor exceeding its ceiling produces an alert and does NOT halt.
```

## C1.8 — HTTP boundary

```
Expose C1 as a service. The other five components are clients — none of them will
ever import this Go package.

ENDPOINTS (all under /v1)
  POST /entries                        body: EntryRequest; Idempotency-Key header
  POST /orders                         create in `quoted`
  GET  /orders/{external_id}
  POST /orders/{external_id}/transitions   body: to_state, expected_version, entry?, reason
  GET  /accounts/{code}/balance        ?as_of_entry_id=N optional
  GET  /balances                       ?prefix=asset:tron:slot: for slot-cap checks
  GET  /trial-balance
  POST /reconciliation/snapshots
  GET  /system/halt
  POST /system/halt                    set or clear; requires operator identity
  GET  /system/invariants              live results of every self-check
  GET  /healthz  GET /readyz  GET /metrics

AUTH
- Service-to-service only. Bearer token per service identity, from config; the token
  maps to the `actor` recorded on every write. Design the interface so mTLS can
  replace it without touching handlers.
- There is no customer-facing auth here and no per-customer scoping. C6 owns that.

ERROR CODES — stable strings, one per condition, never reused, documented in
docs/errors.md:
  409 idempotency_conflict      same key, different payload
  422 unbalanced_entry
  422 asset_mismatch
  423 system_halted
  409 illegal_transition
  409 version_conflict
  404 account_not_found / order_not_found
  400 invalid_amount            includes too many decimal places
  500 internal

RULES
- Request bodies carry amounts as DECIMAL STRINGS ("2990.700000"), never as JSON
  numbers. JSON numbers are floats in most clients and will silently lose precision.
  Reject a JSON number in an amount field with invalid_amount. This is not
  pedantry — it is the most likely way this system loses money.
- Every write handler requires an Idempotency-Key header. No header, no write.
- OpenAPI 3.1 spec generated or hand-maintained in docs/openapi.yaml, and a test
  that asserts every route is present in it.

ACCEPTANCE
- Golden-file tests for every error condition: exact status, exact code string.
- An amount sent as a JSON number is rejected.
- Replaying a POST /entries with the same Idempotency-Key returns 200 with the same
  entry id and a Replayed indicator, not 201.
- Metrics exposed: entries_total, entry_errors_total by code, halt_state gauge,
  orders_by_state gauge, recon_drift_units histogram, recon_lag_seconds.
```

## C1.9 — The replay harness (this is the ship gate)

```
Build a deterministic simulator that hammers the ledger with the scenarios that
actually happen. This is the acceptance gate for C1 as a whole. Nothing ships
without it green.

cmd/replay/main.go, also runnable as a Go test in CI.

- Seeded PRNG. Same seed = byte-identical run. Print the seed on failure.
- Generates 10,000 orders with a configurable scenario mix, default:
    72%  clean happy path (quoted -> funded -> screened -> dispatching -> settled)
     6%  duplicate idempotency keys, half concurrent, half sequential
     4%  reorg before dispatch (scenario A)
   0.5%  reorg after settlement (scenario B) — must halt every time
     5%  screening hold, then release
     2%  screening hold, then reject and refund
     4%  quote expiry, including a deposit landing after expiry
     3%  overpay / underpay / dust deposit amounts
     2%  Sweep batch where 40 of 50 recipients settle and 10 fail
   1.5%  non-retryable dispatch failure -> held, conversion reversed
- Runs with realistic concurrency (default 32 workers), not serially.
- Halt-aware: when a scenario halts the system, the harness records it, clears the
  halt as a simulated operator, and continues — then asserts at the end that the
  halt count equals exactly the number of halt-triggering scenarios injected. Not
  more (spurious halts are as bad as missing ones), not fewer.

FINAL ASSERTIONS — all must hold:
1. TrialBalance() == 0 for every asset.
2. VerifyBalances() returns nothing.
3. Every order is in a terminal state, or in `held` with a recorded reason.
4. order_transitions contains no pair outside the C1.5 transition table.
5. journal_entries row count == number of distinct idempotency keys used.
6. Every reversal has exactly one parent and no reversal is itself reversed.
7. sum(expense:loss:reorg) == sum of amount_out across scenario-B orders, exactly.
8. Halt count == injected halt-trigger count.
9. Zero deadlocks, zero panics, zero unexplained errors. Any error returned that the
   harness did not deliberately provoke fails the run.

PERFORMANCE TARGET: under 60 seconds on a laptop. If it is slower, the ledger is too
slow — the production system does ~100 orders/day and the harness does 10,000. A slow
harness means a design problem, not a harness problem.

DELIVERABLE: a Makefile target `make gate` that runs it and exits non-zero on any
assertion failure, plus a one-page report printed at the end showing scenario counts,
halt events, and final trial balance per asset.
```

## §B — The conversion entry (review this before building anything)

This is the design decision everything else rests on. **BEP20 and TRC20 USDT are separate assets.** A conversion is therefore not a transfer — it is an exchange, recorded as one entry touching two assets, each balancing to zero independently.

Worked example: $3,000 Standard order. Fee 25 bp = $7.50, network fee $1.80, payout $2,990.70.

**E1 — deposit reaches 15 confirmations** (`quoted → funded`)

```
DR  asset:bsc:deposit:1042     +3000.000000  USDT_BEP20
CR  liability:customer:acme    -3000.000000  USDT_BEP20
                                ─────────────  BEP20 sums to 0 ✓
```

**E2 — conversion** (`screened → dispatching`) — one entry, two assets

```
DR  liability:customer:acme    +3000.000000  USDT_BEP20    we no longer owe BEP20
CR  position:corridor          -3000.000000  USDT_BEP20
                                ─────────────  BEP20 sums to 0 ✓
DR  position:corridor          +3000.000000  USDT_TRC20
CR  liability:customer:acme    -2990.700000  USDT_TRC20    we now owe TRC20
CR  revenue:fee                   -7.500000  USDT_TRC20
CR  revenue:network_fee           -1.800000  USDT_TRC20
                                ─────────────  TRC20 sums to 0 ✓
```

**E3 — payout confirmed to SR finality** (`dispatching → settled`)

```
DR  liability:customer:acme    +2990.700000  USDT_TRC20
CR  asset:tron:slot:3          -2990.700000  USDT_TRC20
```

**E4 — energy cost** (posted independently by C4, in TRX)

```
DR  expense:energy                +2.438000  TRX          $0.829 at TRX $0.34
CR  asset:tron:energy_wallet      -2.438000  TRX
```

**E5 — treasury rebalance closes the position** (posted by the treasury runbook)

```
CR  asset:cex:binance          -3000.000000  USDT_BEP20
DR  position:corridor          +3000.000000  USDT_BEP20
                                ─────────────  BEP20 sums to 0 ✓
CR  position:corridor          -3000.000000  USDT_TRC20
DR  asset:tron:slot:3          +2999.550000  USDT_TRC20
DR  expense:rebalance              +0.450000  USDT_TRC20   1.5 bp
                                ─────────────  TRC20 sums to 0 ✓
```

**Why `position:corridor` matters.** Between E2 and E5 the ledger is honest about something the business genuinely is: we have paid out TRC20 we did not yet hold, backed by BEP20 we hold but have not yet moved. The balance of `position:corridor` **is** the rebalancing backlog, in real units, continuously. It returns to zero per asset when inventory catches up.

That makes it three things at once: the treasury loop's work queue, the direct measure of how close the $255k float ceiling is, and — because a growing corridor position with a healthy trial balance means *slow*, not *broken* — the reason C1.7 alerts on it rather than halting.
